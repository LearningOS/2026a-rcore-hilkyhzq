## 目标与环境

在原有线程、互斥锁、信号量和条件变量实现上，增加按进程启用的死锁检测。检测到当前资源请求会形成无可完成的等待状态时，返回 `-0xdead`，不实际阻塞该请求。工具链、QEMU、固件、固定官方检查器和测试程序版本与前述报告相同。

本分支也补齐了原模板的时间查询、匿名映射、spawn、优先级和文件状态/链接接口，按第八章的进程与线程分离结构适配。内存和 FD 表属于进程，调度上下文属于线程。未把第五章的整个任务结构直接合并进来。

## 资源模型

每个进程持有独立 DeadlockState。资源键由“互斥锁/信号量种类”和该进程中的 ID 组成，避免两个种类的相同数字 ID 冲突。每种资源记录可用单位数、各线程的已分配数量、尚未满足的请求队列。

线程的内部 actor 编号使用独立递增编号，而非可回收的用户 TID。因此旧线程退出后，即使 TID 被复用，新线程也不会继承其持有记录。退出线程仍持有的资源不会被安全性分析假定能自动释放；已不持有资源的退出线程不保留退休记录。

`enable_deadlock_detect` 只接受 0 或 1。关闭检测时仍维护实际分配记录，仅关闭请求拒绝，这样开启检测时已有持有关系不会丢失。

## 请求检查算法

1. 将本次请求暂时加入对应资源的等待队列。
2. 若启用检测，以当前 Available 为 Work，收集所有持有或请求资源的活动线程。
3. 找到其当前请求可由 Work 满足的线程，模拟其完成并释放已经持有的资源，将这些资源加回 Work。
4. 重复直到没有进展；若仍存在不能完成的活动线程，则拒绝并回滚本次请求。
5. 请求通过后，若有可用单位就登记分配；否则保留等待记录，再调用原有阻塞/自旋原语。

这检查的是已经发生的互斥锁/信号量分配和当前请求，不是对未来程序执行、任意消息依赖或 join/条件变量依赖的通用静态证明。

## 与实际同步原语保持一致

阻塞互斥锁和信号量按 FIFO 唤醒。释放资源时，若已有等待线程，元数据立即将该单位交接给首个等待者，再由原有原语唤醒同一线程，避免它尚未恢复执行时资源被分析为“空闲”。

自旋互斥锁的实际胜出顺序不一定是 FIFO，因此释放时只标记可用，在真正获得锁的线程返回时再确认分配。模型测试覆盖等待者以相反顺序胜出的情况。

进入可能阻塞的原语前释放进程内部借用和临时进程 Arc，不让这些借用跨越调度点。条件变量等待经由相同的互斥锁解锁、登记等待、阻塞、重新加锁流程更新计数。该课程为单核、内核陷入期间不启用抢占，解锁与进入条件等待队列之间不会切换任务；本实现没有宣称适用于多核而无需额外同步。

互斥锁解锁检查持有者；信号量 up 允许由非持有者发布单位，保留常见生产者/消费者使用方式。无效的同步对象 ID 返回失败。
